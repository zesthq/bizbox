## Shipped this week

### Human-in-the-loop handoff, end to end

The biggest theme this week was making the boundary between autonomous agent work and human decision-making explicit, observable, and reliable. Three PRs landed together to close that loop:

**[#38 — Human handoff logging and notification](https://github.com/zesthq/bizbox/pull/38)** _(v0.0.13, @adPalafox)_
Bizbox now emits a dedicated event whenever an issue parks itself waiting for a human — whether that's a confirmation request, a question, or a human-owned blocker. The event deduplicates across runs so operators don't get spammed, and it feeds the inbox badge count. This is the foundation everything else this week builds on.

**[#42 — ClickUp awaiting-human approval polling](https://github.com/zesthq/bizbox/pull/42)** _(v0.0.16, @adPalafox)_
Once an issue is parked, Bizbox now polls the ClickUp chat message that was posted for that handoff. A direct reply or a positive reaction on that message is detected and bridged back into Bizbox's workflow as an approval signal. Configurable positive-reaction set, deduplication, and test coverage included.

**[#51 — Confirmation notifications in the inbox](https://github.com/zesthq/bizbox/pull/51)** _(v0.0.20, @angelofallars)_
The inbox now surfaces "Confirmation requested" and "Questions requested" notifications for every human on the company. The sidebar badge updates in real time. Operators no longer need to hunt for parked issues — the inbox tells them.

Together these three PRs mean: agent parks → ClickUp message sent → human replies → Bizbox detects it → agent resumes. The full handoff cycle is now wired.

**[#36 — ClickUp super agents](https://github.com/zesthq/bizbox/pull/36)** _(v0.0.20, @DennisDenuto)_

The adapter runs as an API-first bridge (not a local process executor), shapes ClickUp task payloads with full issue context, and supports an `automation_trigger` mode so ClickUp Automations can hand off to the ClickUp AI agent without browser automation. ## Decisions

**Separate `awaiting_human` from `blocked`.** The team made a deliberate call to treat human-blocked work as a distinct state rather than overloading `blocked`. The reasoning: dependency blockers may resolve without human input; human-decision blockers require an explicit handoff and a clear ask. Mixing them made it impossible to route notifications correctly or measure how long humans were actually in the critical path. The `awaiting_human` status is now a protected control-plane pause, not a cosmetic label. (See also the [May Deep Dive draft](https://github.com/zesthq/bizbox/pull/45) for the full architectural analysis — the complete post is coming next week.)

**ClickUp as an approval signal surface, not a source of truth.** The ClickUp polling bridge (#42) was designed with a specific constraint: a reply or reaction in ClickUp is only a _signal_ until Bizbox accepts the matching `request_confirmation` interaction. ClickUp is not the source of truth for workflow state. This keeps the Bizbox issue graph authoritative and prevents race conditions where a ClickUp reaction fires before the interaction is registered.

**Audience field as a first-class property.** Rather than inferring visibility from document type or location, the team added an explicit `audience` field. The default for public drafts is `human`; agents producing internal work products must explicitly set `internal`. This makes leakage harder to do accidentally.

---

## Trade-offs

**Polling vs. webhooks for ClickUp approval.** The current ClickUp approval bridge polls for replies and reactions rather than receiving webhooks. Polling adds latency (approval detection is bounded by the poll interval) and burns API quota. The trade-off was accepted because ClickUp's webhook surface for chat reactions is less reliable than its REST API, and the team wanted a working bridge now rather than a fragile one. A webhook upgrade is the natural next step once the polling path is proven in production.

**Heartbeat-promoted deliverables are best-effort.** The new heartbeat deliverable extraction (#49) uses pattern matching on run output. Agents that don't follow the tagging convention will have their deliverables silently skipped rather than erroring. This was a deliberate choice to avoid breaking existing heartbeat runs, but it means the feature's value depends on agents adopting the tagging convention consistently.

---

## Open challenges

**ClickUp approval latency in production.** The polling bridge is new and untested at scale. We don't yet know what poll interval is safe without hitting ClickUp rate limits, and we don't know how often the "positive reaction" heuristic will produce false positives. Monitoring this in the first week of production use is the immediate next step.

**Deliverable tagging adoption.** The heartbeat-promoted deliverables feature (#49) is only as good as the tagging discipline of the agents using it. There's no enforcement yet — an agent that produces a deliverable in a non-standard format will silently miss the promotion. A linting pass or schema validation on run output would close this gap.

**Builder API route migration.** Moving the builder under company routes (#47) is the right long-term shape, but any clients that hardcoded the old instance-root path will break silently. The team should audit known consumers before the next release.
