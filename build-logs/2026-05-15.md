## Shipped this week

### Human-in-the-loop handoff, end to end

The big one this week: the full agent → human → agent cycle is wired. Three PRs landed together to close it.

**[#38 — Human handoff logging and notification](https://github.com/zesthq/bizbox/pull/38)** _(v0.0.13, @adPalafox)_
When an issue parks waiting for a human — confirmation request, question, or human-owned blocker — Bizbox now emits a dedicated event. It deduplicates across runs so operators don't get spammed, and it feeds the inbox badge count. Everything else this week builds on this.

**[#42 — ClickUp awaiting-human approval polling](https://github.com/zesthq/bizbox/pull/42)** _(v0.0.16, @adPalafox)_
Once parked, Bizbox polls the ClickUp chat message posted for that handoff. A direct reply or positive reaction gets detected and bridged back as an approval signal. Configurable reaction set, deduplication, test coverage.

**[#51 — Confirmation notifications in the inbox](https://github.com/zesthq/bizbox/pull/51)** _(v0.0.20, @angelofallars)_
"Confirmation requested" and "Questions requested" items now show up in the board inbox, and the sidebar badge counts them. No more hunting for parked issues — they surface alongside other actionable work.

Put together: agent parks → ClickUp message sent → human replies → Bizbox detects it → agent resumes.

## Decisions

**`awaiting_human` is not `blocked`.** These are now distinct states. Dependency blockers can resolve on their own; human-decision blockers need an explicit handoff and a clear ask. Conflating them made notification routing impossible and hid how long humans were actually in the critical path. `awaiting_human` is a protected control-plane pause now, not a catch-all label. (Full architectural breakdown in the [May Deep Dive draft](https://github.com/zesthq/bizbox/pull/45) — post coming next week.)

**ClickUp is a signal surface, not a source of truth.** The polling bridge (#42) has a deliberate constraint: a ClickUp reply or reaction is only a _signal_ until Bizbox accepts the matching `request_confirmation` interaction. The issue graph stays authoritative, which prevents race conditions where a ClickUp reaction fires before the interaction is registered.

**`audience` is explicit, not inferred.** Rather than deriving visibility from document type or location, there's now a first-class `audience` field. Public drafts default to `human`; internal work products require an explicit `internal`. Accidental leakage gets harder.

---

## Trade-offs

**Polling instead of webhooks for ClickUp approval.** The bridge polls for replies and reactions rather than receiving webhooks — which adds latency bounded by the poll interval and burns API quota. The call was deliberate: ClickUp's webhook surface for chat reactions is less reliable than its REST API, and a working bridge now beats a fragile one later. Upgrading to webhooks is the obvious next step once polling is proven in production.

**Heartbeat-promoted deliverables are best-effort.** The extraction in #49 uses pattern matching on run output. Agents that don't follow the tagging convention will have deliverables silently skipped rather than errored — a deliberate choice to avoid breaking existing heartbeat runs. The feature's value depends on consistent tagging adoption.

---

## Open challenges

**ClickUp approval latency in production.** The polling bridge is new and untested at scale. Safe poll intervals and false-positive rates for the "positive reaction" heuristic are still unknown. First week of production use will tell us a lot.

**Deliverable tagging adoption.** No enforcement yet — an agent producing a deliverable in a non-standard format will silently miss promotion. A linting pass or schema validation on run output would close this gap.

**Builder API route migration.** Moving the builder under company routes (#47) is the right long-term shape, but clients that hardcoded the old instance-root path will break silently. Known consumers should be audited before the next release.
