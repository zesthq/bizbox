## Shipped this week

### Human-in-the-loop handoff, end to end

Most of the week went into closing the loop on human handoffs. The pieces were mostly there: issues could park waiting for a human, ClickUp messages were going out. But the return path wasn't wired and the inbox wasn't surfacing any of it. Three PRs fixed that.

**[#38 — Human handoff logging and notification](https://github.com/zesthq/bizbox/pull/38)** _(v0.0.13, @adPalafox)_
Bizbox now emits a dedicated event when an issue parks for a human (confirmation request, question, or blocker). Deduplicates across runs, feeds the inbox badge count.

**[#42 — ClickUp awaiting-human approval polling](https://github.com/zesthq/bizbox/pull/42)** _(v0.0.16, @adPalafox)_
Bizbox polls the ClickUp chat message posted for the handoff. A direct reply or positive reaction gets detected and bridged back as an approval signal. Configurable reaction set, deduplication, test coverage.

**[#51 — Confirmation notifications in the inbox](https://github.com/zesthq/bizbox/pull/51)** _(v0.0.20, @angelofallars)_
"Confirmation requested" and "Questions requested" items show up in the board inbox now, and the sidebar badge counts them. Parked issues are no longer invisible.

### ClickUp super agents

**[#36 — ClickUp super agents](https://github.com/zesthq/bizbox/pull/36)** _(v0.0.20, @ralphbibera)_
`clickup_agent_ref` is a new adapter that treats ClickUp-native automations as first-class agents in Bizbox. It's an API bridge, not a local process executor. It shapes task payloads with full issue context and has an `automation_trigger` mode so ClickUp Automations can hand off to the ClickUp AI agent without browser automation.

## Decisions

**`awaiting_human` vs `blocked`.** These are separate states now. The distinction matters because dependency blockers can resolve without anyone doing anything; human-decision blockers need an explicit handoff and a clear ask. Mixing them made it impossible to route notifications correctly or measure how long humans were actually holding things up. `awaiting_human` is a control-plane pause, not a label. (There's a full write-up in the [May Deep Dive draft](https://github.com/zesthq/bizbox/pull/45) if you want the details; post coming next week.)

**ClickUp as a signal, not a source of truth.** The polling bridge (#42) was built with a specific constraint: a ClickUp reply or reaction is only a signal until Bizbox accepts the matching `request_confirmation` interaction. The issue graph stays authoritative. This matters because ClickUp reactions can fire before the interaction is registered, and you don't want that to silently advance workflow state.

**Explicit `audience` field.** Rather than inferring visibility from document type or location, there's now a first-class field. Public drafts default to `human`; anything internal has to be explicitly marked. Harder to leak by accident.

---

## Trade-offs

**Polling for ClickUp approval, not webhooks.** Polling adds latency and burns API quota. The decision was to ship something that works reliably now rather than depend on ClickUp's webhook surface for chat reactions, which is less stable than the REST API. Webhooks are the obvious upgrade path once the polling approach is validated in production.

**Heartbeat deliverable extraction is best-effort.** The pattern matching in #49 will silently skip deliverables from agents that don't follow the tagging convention. That was intentional: erroring would have broken existing heartbeat runs. Whether the feature actually gets used depends on agents adopting consistent tagging.

---

## Open challenges

**ClickUp approval latency.** The polling bridge hasn't been tested at scale. We don't know yet what poll interval is safe, or how often the "positive reaction" heuristic produces false positives. First week in production will be informative.

**Deliverable tagging.** No enforcement. An agent that produces a deliverable in a non-standard format will miss promotion silently. Schema validation or a linting pass on run output would fix this.

**Builder route migration.** The move to company-scoped routes (#47) is correct long-term, but any client that hardcoded the old path will break without warning. Worth auditing known consumers before the next release.
