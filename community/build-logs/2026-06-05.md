# Bizbox Build Log — Week of 2026-06-01

**The awaiting-human bridge is complete.** The ClickUp handoff system — three weeks in the making — shipped its final piece this week as a clean, provider-agnostic plugin. On top of that, Google ADK adapter support (merged last week) got its first tagged release, and a CI headless flakiness fix landed. Here's what changed.

---

## Shipped This Week

### feat(awaiting-human): ClickUp bridge adapter as pure plugin — [PR #78](https://github.com/zesthq/bizbox/pull/78)

This is the capstone of the awaiting-human bridge series. The ClickUp transport and adapter are now a pure plugin that registers through `AwaitingHumanBridgeRegistry` — the bridge core stays completely provider-agnostic. What that means in practice: when an agent needs a human to approve something or answer a question, Bizbox sends a formatted ClickUp message, polls for a reply or reaction, and resumes the agent automatically. The same bridge core will work for Slack, Discord, or any future provider without touching the core.

The PR adds the full ClickUp transport (send, poll, reactions, approval/rejection signal detection), message templates for `request_confirmation` and `ask_user_questions` interaction types, and acknowledgement reactions (`brain_is_thinking` on send, `white_check_mark` on resolution, `x` on failure).

### ci: use runner Chrome for headless workflows — [PR #84](https://github.com/zesthq/bizbox/pull/84)

Flaky CI timeouts on headless browser jobs traced back to browser bootstrap overhead, not app logic. The fix mirrors the upstream Paperclip pattern: target the preinstalled Chrome binary via `PAPERCLIP_PLAYWRIGHT_CHANNEL=chrome` across the PR, e2e, and release-smoke workflows. Same coverage, less setup noise. The underlying bootstrap timing is a known area for future improvement.

### Release: v2026.601.0 — [release notes](https://github.com/zesthq/bizbox/releases/tag/v2026.601.0)

`v2026.601.0` is the first tagged release to bundle the full awaiting-human bridge series. It includes:

- **PR #74** — bridge configuration schema and settings (merged 2026-05-28, first tagged release this week)
- **PR #76** — bridge retry and reply dedupe (merged 2026-05-28, first tagged release this week)
- **PR #72** — Google ADK agent adapter (merged 2026-05-28, first tagged release this week)
- **PR #78** — ClickUp bridge adapter as pure plugin (merged this week)
- **PR #84** — CI headless fix (merged this week)

PRs #72, #74, and #76 were covered in last week's Build Log as merged-but-unreleased. This week they crossed the finish line into a tagged release.

---

## Decisions

**Provider-agnostic bridge core is a hard constraint.** The ClickUp adapter was explicitly ported as a pure plugin rather than hardcoded into bridge core files. The registry pattern (`AwaitingHumanBridgeRegistry`) is the contract: any future provider (Slack, Discord, email) registers the same way. This decision was made in PR #78 after an earlier branch had ClickUp hardcoded — that approach was rejected.

**Interaction-scoped dedupe over message-level dedupe.** PR #76 chose to scope deduplication to the interaction ID rather than the message content. This means the same human question can be re-asked if the interaction is genuinely new, but retries within the same interaction never produce duplicate messages.

---

## Trade-offs

The bridge polling model is synchronous from the agent's perspective — the agent parks in `awaiting_human` and resumes only after the bridge detects a reply or reaction. This is simple and auditable, but it means latency is bounded by the ClickUp polling interval, not by real-time push. For most approval workflows this is fine; for time-sensitive escalations it's worth watching.

The Google ADK adapter ships without a live integration test run (noted in PR #72). Unit tests cover event parsing and execution behaviour, but the end-to-end path through a real ADK runtime wasn't validated in CI this week. That's a known gap.

---

## Open Challenges

- **Bridge provider coverage.** ClickUp is the only live transport. The registry is ready for Slack and Discord, but those adapters don't exist yet. If your team uses a different channel for human approvals, you're waiting on a future PR.
- **ADK live integration tests.** The Google ADK adapter needs an end-to-end test run against a real ADK runtime before it can be considered fully production-hardened.
- **Headless CI bootstrap timing.** The runner Chrome fix reduces flakiness significantly; the root cause (bootstrap timing variance) is a known area for future improvement.
