# Bizbox Build Log — Week of 2026-06-01

Five PRs merged (2026-05-31 through 2026-06-03), five releases shipped, two Release CI pipeline failures surfaced mid-week. The headline: Workflows land as a first-class Bizbox primitive — company-scoped, ADK-backed, with topological pipeline graphs, live console output, and human handoffs. The week also closed the awaiting-human loop: the ClickUp bridge adapter shipped as a pure plugin, completing the approval-chain infrastructure built across the last three weeks.

## Shipped This Week

### 🔁 Workflows: a new company-scoped primitive
**PR [#86](https://github.com/zesthq/bizbox/pull/86) · @DennisDenuto · merged 2026-06-03 · v2026.603.0**

The largest change this week introduces `Workflows` as a distinct Bizbox primitive, separate from issues and routines. A workflow is a multi-phase pipeline backed by Google ADK: it has a database record, run history, deliverables, and a UI that renders phases as a topological graph with live phase state and console output.

Key additions:
- New DB schema, API routes, and JWT-protected runtime callbacks for workflow runs.
- ADK project analysis so the pipeline structure is inferred automatically and rendered as a graph.
- Human handoff slots within a pipeline run — agents can pause and wait for operator input without blocking the whole workflow.
- Mixed deliverable support: a single workflow run can surface structured data, documents, and raw console output side by side.
- UI navigation, workflow detail/run views, and pipeline graph rendering.

This is the first step toward long-running, multi-agent orchestration that doesn't fit neatly into the issue/heartbeat model.

### 🌉 ClickUp bridge adapter: the approval loop closes
**PR [#78](https://github.com/zesthq/bizbox/pull/78) · @ralphbibera · merged 2026-05-31 · v2026.601.0**

The three-PR awaiting-human bridge series is complete. PRs #74 and #76 (last week) shipped the provider-agnostic bridge infrastructure and company-scoped configuration; PR #78 delivers the ClickUp transport as a pure plugin.

What landed:
- `clickup-awaiting-human-transport.ts` — HTTP transport for the ClickUp Chat API (send, poll, reactions, approval/rejection signal detection).
- `clickup-awaiting-human-bridge-adapter.ts` — implements the `AwaitingHumanBridgeAdapter` registry interface; ClickUp is registered as `"clickup"` at server startup.
- Reaction semantics: `brain_is_thinking` on send; `white_check_mark` for approved/rejected/superseded; `x` for failed cleanup paths.
- ClickUp message templates for `request_confirmation` and `ask_user_questions` interaction types.
- Stable `reply.id` requirement before emitting reply events; malformed replies are skipped with logging.

The full approval loop — company settings → bridge core → ClickUp delivery → human reply → agent wake — is now closed. Adding a second provider (Slack, Discord) means writing a new adapter against the same registry interface; the bridge core is untouched.

### 🐛 Google ADK: strip frontmatter from AGENTS.md instructions
**PR [#87](https://github.com/zesthq/bizbox/pull/87) · @ralphbibera · merged 2026-06-02 · v2026.602.1**

YAML frontmatter in `AGENTS.md` is used by Paperclip for metadata and discovery — but the Google ADK adapter was passing the raw file (frontmatter and all) as agent instructions. ADK treated the YAML block as part of the instruction text, producing garbled prompts for ADK-backed agents. The fix strips frontmatter before forwarding instructions to the ADK runtime. Simple change, material impact on ADK agent behaviour.

### 🔂 Issue origin handling: suggested-task deduplication and fingerprinting
**PR [#88](https://github.com/zesthq/bizbox/pull/88) · @adPalafox · merged 2026-06-02 · v2026.602.0**

Accepting the same `suggest_tasks` interaction bundle multiple times used to create duplicate child issues. This PR fixes that with SHA-256 fingerprinting of the full task spec: if a matching child issue already exists under the same parent, the service reuses it instead of creating a duplicate. Blocker relationships are preserved on reuse. The change also adds `"suggested_task"` as an explicit `originKind` constant so the dedup path is unambiguous at the data layer.

Note: fingerprint matching is strict. A suggested task that differs by even one field (e.g. priority changed) creates a new child issue rather than updating the existing one.

### 🧪 CI: headless Chrome on runner for e2e workflows
**PR [#84](https://github.com/zesthq/bizbox/pull/84) · @ralphbibera · merged 2026-06-01 · v2026.601.0**

E2e tests for headless control-plane workflows were timing out on CI due to browser bootstrap latency, not application logic. Switching to the runner's native Chrome instance eliminates the cold-start delay and restores green e2e coverage.

## Decisions

**Workflows are a primitive, not a plugin.** The team built `Workflows` into the Bizbox data model (new DB tables, API routes, shared contracts) rather than layering them on top of routines or issues. Workflows need their own run lineage, deliverable surface, and pipeline graph that existing primitives can't cleanly host. The trade-off is more surface area to maintain.

**ADK pipeline structure inferred, not declared.** Rather than requiring operators to declare the pipeline graph upfront, PR #86 adds ADK project analysis so the phase structure is inferred from the ADK project definition at run time. This reduces operator configuration but means the graph is only as accurate as ADK's own project metadata.

**ClickUp adapter as registry plugin, not bridge-core coupling.** PR #78 is the payoff of the architectural decision made in PRs #74 and #76: bridge core is strictly provider-agnostic, and each transport registers via `AwaitingHumanBridgeRegistry`. The ClickUp adapter ships without touching any bridge core files.

**Fingerprint-based deduplication over timestamp guards.** SHA-256 fingerprinting of the full task spec was chosen for suggested-task dedup. The stronger guarantee is worth the extra hashing overhead at issue-creation time.

---

## Trade-offs

- **Workflows ship without end-to-end integration tests.** PR #86 includes server, shared, and UI unit tests plus local verification, but there is no automated test covering the full path: workflow create → ADK run → phase graph render → human handoff → deliverable surface.
- **v2026.601.0 bundles three weeks of previously-untagged PRs.** PRs #72, #74, #76, and #78 all predate the June 1 window but shipped together in the v2026.601.0 tag. If you were waiting on a stable tag for the awaiting-human bridge, Google ADK adapter, or ClickUp transport, v2026.601.0 is it.
- **Fingerprint deduplication is strict.** Any single-field difference creates a new child issue. Correct for data integrity, but operators who expect fuzzy dedup will see new issues where they expected reuse.

## Open Challenges

- **Two Release CI failures this week.** The Release workflow failed after both PR #87 (v2026.602.1, run [#26806281211](https://github.com/zesthq/bizbox/actions/runs/26806281211)) and PR #86 (v2026.603.0, run [#26858452717](https://github.com/zesthq/bizbox/actions/runs/26858452717)). Two failures in a four-release week is a pattern, not noise. Both releases appear to have shipped (the tags exist), but the Release workflow health is worth investigating.
- **Workflows end-to-end test gap.** The pipeline graph, human handoff, and deliverable surface are new code with no automated integration coverage. Non-trivial reliability risk for early adopters; integration tests are the clear next step.
- **Two pre-existing test failures in `pnpm test`.** PR #78 noted two unrelated test failures at merge time (`agent-permissions-routes.test.ts` and `company-portability-routes.test.ts`). These were pre-existing and out of scope for the PR, but they're now logged and should be resolved before they mask real regressions.
