# Build Log: May 5–11, 2026

Five releases, fifteen PRs merged, and a clear theme this week: **refining the agent execution surface**—better observability, cleaner state management, and smarter human-in-the-loop flows.

## Shipped this week

### `awaiting_human` issue status

[#33](https://github.com/zesthq/bizbox/pull/33) introduces a new `awaiting_human` status to separate human-blocked work from dependency-blocked work. Previously, both landed in `blocked`, making it hard to tell whether an issue was waiting on a human decision or another agent's child task.

**Why it matters:** Agents can now distinguish "needs Dennis to approve" from "needs child issue CITAAAA-42 to finish." The orchestration engine uses this signal to route work correctly and avoid waking agents prematurely.

**Trade-off:** One more status for humans to track. We chose clarity over simplicity—knowing *why* something is blocked matters more than keeping the status list short.

### Archived routines toggle

[#37](https://github.com/zesthq/bizbox/pull/37) adds a UI toggle for showing or hiding archived routines. Operators can now clean up their routine list without losing visibility into past work.

**Decision:** We default to hiding archived routines. Active work should be front and center. Operators who need history can flip the toggle.

### OpenTelemetry expansion (continued)

[#34](https://github.com/zesthq/bizbox/pull/34) and [#26](https://github.com/zesthq/bizbox/pull/26) expand OpenTelemetry instrumentation—more metrics, more traces, and better coverage of agent execution paths.

**Open challenge:** We're still figuring out *which* metrics matter. We're instrumenting everything we can think of, then we'll prune based on what operators actually use. If you're running Bizbox and have metric requests, let us know.

### Bizbox Journey Story

[#32](https://github.com/zesthq/bizbox/pull/32) adds the **Bizbox Journey Story**—a narrative document explaining the Bizbox vision, philosophy, and roadmap. This is part of our build-in-public commitment: we want the community to understand not just *what* Bizbox does, but *why* we built it this way.

**Why now:** We're seeing more inbound questions about Bizbox's design choices. This doc codifies our answers in one place.

### Deliverables tab

[#28](https://github.com/zesthq/bizbox/pull/28) adds a **Deliverables** tab under the Work section. Operators can now see all artifacts and work products in one place—documents, code outputs, reports, analysis—without hunting through issue threads.

**Trade-off:** Another tab in the UI. We chose discoverability over minimalism. Artifacts are first-class outputs; they deserve a dedicated surface.

### Auto-post templated issue comments on inbox approval decisions

[#29](https://github.com/zesthq/bizbox/pull/29) automates a common manual step: when an operator approves or rejects an inbox item, Bizbox now posts a templated comment explaining the decision. This gives agents (and humans reading the thread later) immediate context about why something was approved or rejected.

**Decision:** Templates over freeform text. Consistency matters more than flexibility here. If the template doesn't fit, operators can still edit the comment manually.

**Open challenge:** We don't yet have templates for every decision type. We're starting with inbox approvals and will expand based on feedback.

### Prior week Build Log published

[#31](https://github.com/zesthq/bizbox/pull/31) merged the Build Log for the week ending May 9, 2026. That log is now live at [build-log-2026-05-09](https://github.com/zesthq/bizbox/releases/tag/build-log-2026-05-09).

**Lesson:** Our own Build Log process is a test case for Bizbox's content-production capabilities. We're dogfooding the `bizbox-build-log-summarizer` and `content-syndication` skills every week.

### Company AI Builder

[#20](https://github.com/zesthq/bizbox/pull/20) landed the full **Company AI Builder** feature—a curated set of mutation tools delivered via a proposal-approval flow. This was actually merged in an earlier cycle but appeared in this week's activity window due to release timing.

**Context:** Phases 0–4 shipped together: read-only spike work (Phase 0), proposal-store infrastructure (Phase 1), mutation tools behind proposals (Phase 2), approval surface for company owners (Phase 3), and basic mutation tool suite (Phase 4).

### Artifact validation and persistence improvements

[#27](https://github.com/zesthq/bizbox/pull/27) hardens artifact validation—enforcing that artifact work products always have attachment-backed metadata and a `createdByRunId`. New schema validators and runtime type guards mean artifact handling is now fail-fast instead of fail-silent.

[#25](https://github.com/zesthq/bizbox/pull/25) adds support for collecting output artifacts from adapter executions (especially OpenClaw Gateway adapters), introduces new types and logic for artifact management, and exposes utilities for artifact-related work products.

**Why this matters:** Agents produce artifacts (deliverables, documents, code outputs). Loose validation meant broken artifact references could propagate through the system. These changes catch errors at the boundary and give operators a clearer view of what was produced.

### Refactor agentParams handling

[#24](https://github.com/zesthq/bizbox/pull/24) fixes a regression introduced in `v0.0.6` where the OpenClaw gateway adapter changed the outbound agent request shape. The fix refactors `agentParams` handling and removes an unused function that was masking the real issue.

**Lesson:** Request shape changes in adapters are easy to miss when tests don't cover the boundary. We added a test to catch this pattern in the future.

### Agent thread chat with optimistic UI

[#21](https://github.com/zesthq/bizbox/pull/21) adds a direct communication channel between operators and agents. Users can now message agents from the agent detail page, with optimistic UI updates for a snappier feel.

**Decision:** We chose optimistic updates over waiting for server confirmation. It makes the UI feel faster. The trade-off: rare cases where the server rejects a message won't be obvious until you refresh. We're watching for confusion signals.

### Routine execution recovery logic

[#22](https://github.com/zesthq/bizbox/pull/22) fixes how Bizbox handles `routine_execution` issues in `blocked` state. Previously, the recovery logic treated blocked routines as failures and tried to resume them prematurely. Now, `blocked` is recognized as a healthy, parked wait state.

**Why this was broken:** Routines often block on human approval or child issue completion. The old logic didn't distinguish "blocked and waiting" from "blocked and stuck." This change codifies the difference.

### Workflow cleanup

[#23](https://github.com/zesthq/bizbox/pull/23) removes the `sync-upstream` workflow. We're switching to manual upstream merges (with AI assistance) for now.

**Why:** Automated upstream sync introduced more conflicts than it saved in merge time. Manual merges with AI assistance give us control without the constant breakage.

## Decisions

- **`awaiting_human` as a first-class status:** Distinguishing human-blocked from dependency-blocked work is worth the complexity of one more status.
- **Default to hiding archived routines:** Active work deserves the spotlight. Operators who need history can opt in.
- **Templates for approval comments:** Consistency over flexibility. We can always add freeform later if templates don't cover enough cases.
- **Optimistic UI updates for agent chat:** Speed over certainty. We're betting users will tolerate rare server rejection cases in exchange for a snappier feel.
- **Blocked routine state is healthy:** Routines can wait. Not every blocked issue is a failure.
- **Manual upstream merges:** Automation failed here. Human-in-the-loop merges with AI assistance work better for our repo.

## Trade-offs

- **`awaiting_human` adds cognitive load:** One more status for humans to track. We chose clarity, but we're watching for confusion.
- **Another UI tab for Deliverables:** We're betting discoverability wins over minimalism. If the tab feels cluttered, we'll revisit.
- **Templated comments limit expression:** We're starting strict. We can loosen later if operators need more flexibility.
- **Optimistic UI hides rare server rejections:** We chose speed. Watching for user confusion.
- **One OpenTelemetry metric expansion at a time:** We're instrumenting broadly, then pruning. Risk: we might miss important signals early.

## Open challenges

- **Which metrics matter?** We're instrumenting everything, but we don't yet know which signals operators will actually use. Feedback welcome.
- **Template coverage for all decision types:** We're starting with inbox approvals. What other decisions need templated comments?
- **Artifact versioning and metadata:** What needs to travel with an artifact? How do we version it? What should the UI surface? Still figuring this out.
- **Approval UX for high-frequency mutations:** Approving every change works for low-frequency operations. It won't scale to high-frequency agent work. Need smarter defaults.
- **Upstream merge strategy:** Manual merges with AI assistance work for now, but they don't scale. We need a better long-term approach.
