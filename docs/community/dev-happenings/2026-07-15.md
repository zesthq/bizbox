# Dev happenings: making workflow runs easier to understand

## Current update

Bizbox is getting better at showing its work.

This week, we shipped a small but meaningful improvement to the workflow detail page: when you open a run, you can now see the operator input that started it, right above the console output. That gives the run a clearer story from beginning to end: what went in, what happened, and what came out.

It is the kind of change that can look modest in a diff and make a real difference in day-to-day engineering. When a workflow behaves unexpectedly, the first question is often, “What did we actually ask it to do?” The answer is now part of the run view.

## What changed

The workflow page now includes a read-only **Operator input** card. It shows the stored input for the selected run and updates when you move through run history, so older runs can be compared without losing their original context.

We also added an empty state for workflows that have not run yet and expanded the page tests around latest runs, historical runs, refresh behaviour, and no-run states. The page received a small visual cleanup at the same time, keeping attention on the information operators need.

This is now merged in [PR #131](https://github.com/zesthq/bizbox/pull/131).

## Why it changed

The decision was driven by a simple principle: operational interfaces should make important context visible where the work is being inspected.

A console can tell us what a workflow did. It cannot, by itself, tell us why that run was started. Keeping the input and output together makes the page easier to audit and reduces the amount of reconstruction an engineer has to do when reviewing a run.

That fits with a broader direction we are exploring in workflow development: make the individual steps easier to understand, keep their behaviour predictable, and share useful building blocks instead of copying the same logic across projects. Clear context is part of that foundation.

## What the team is learning

Good developer experience is often about removing small gaps between cause and effect.

A visible input makes debugging conversations more concrete. A historical run that preserves its own context is easier to compare. A focused test makes the intended behaviour easier to protect. None of these is a flashy new capability, but together they make the system more legible—and legibility is what lets teams move quickly without guessing.

We are also learning to keep the shape of the work proportional to the problem. This change stays focused on the workflow detail surface, with no change to the underlying run data or execution path. That keeps the risk low while improving the operator experience immediately.

## What’s next

We’ll keep looking for places where important workflow context is technically available but hard to see. The next useful improvements will come from the same question: when someone is trying to understand a run, what do they need in front of them?

If you work with Bizbox workflows, tell us which part of a run you most often have to reconstruct. Those small friction points are good signals for the next round of improvements.
