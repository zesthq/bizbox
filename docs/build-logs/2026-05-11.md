# Build Log: Week Ending May 11, 2026

We shipped **17 PRs** and **9 version releases** this week across artifact persistence, UI polish, observability, and human-handoff workflows. The team moved fast on the agent thread chat, the new `awaiting_human` status, and templated issue comments — all steps toward making Bizbox feel less like "the agent did something" and more like "we're working together."

## Shipped This Week

### Agent Thread Chat & Optimistic UI ([#21](https://github.com/zesthq/bizbox/pull/21))
Real-time chat threads for agents. Updates appear instantly in the UI while the backend catches up. This was a bigger lift than the PR size suggests — plumbing WebSocket state through React query invalidation without flickering is never simple.

### Refactor agentParams Handling ([#24](https://github.com/zesthq/bizbox/pull/24))
Fixed a regression in the OpenClaw gateway adapter that caused agent executions to fail in production. The adapter was sending a top-level `paperclip` field that OpenClaw rejected. This hotfix restored the documented pre-release behavior by stripping that field before the request. Small diff, big impact — agent runs that were stuck `blocked` are now flowing again.

### Artifact Persistence for Issue-Backed Runs ([#25](https://github.com/zesthq/bizbox/pull/25))
Agents can now save work products (drafts, reports, configs) against the issue that triggered them. The UI shows these under a new Deliverables tab ([#28](https://github.com/zesthq/bizbox/pull/28)). Before this week, agents wrote files but we had no durable link from the issue to what they produced. Now we do.

### Build Log: Week Ending May 9, 2026 ([#31](https://github.com/zesthq/bizbox/pull/31))
Landed the previous week's Build Log covering agent capability and trustworthiness improvements. This is part of our weekly build-in-public cadence — every merged Build Log becomes the source of truth for that week's dev community updates.

### The `awaiting_human` Status ([#33](https://github.com/zesthq/bizbox/pull/33))
New issue status to separate "blocked on a person" from "blocked on another task." Agents can mark issues `awaiting_human` with a clear ask (approval needed, question unanswered, decision required). The status shows up in filters and dashboards so operators can triage human-blocked work separately.

### Human Handoff Logging & Notifications ([#38](https://github.com/zesthq/bizbox/pull/38))
When an agent moves an issue to `awaiting_human`, Bizbox now logs the handoff event and can notify the right person (Slack, email, in-app). We're not spamming anyone yet — notifications are opt-in per agent and per channel — but the plumbing is there.

### Templated Issue Comments on Inbox Approval ([#29](https://github.com/zesthq/bizbox/pull/29))
Agents can post a pre-defined comment to an issue thread when they approve/reject/defer an inbox item. Reduces the "what happened here?" confusion when a triage agent closes an issue without explanation.

### Observability: More Metrics & Traces ([#26](https://github.com/zesthq/bizbox/pull/26), [#34](https://github.com/zesthq/bizbox/pull/34))
Added OpenTelemetry metrics for agent run latency, artifact save operations, and issue status transitions. Traces now capture routine execution spans end to end. We're still tuning what to sample, but the instrumentation is in place.

## Decisions

We split "blocked" into two statuses: `blocked` (waiting on another task) and `awaiting_human` (waiting on a person). This felt obvious in hindsight, but it took us weeks to notice that operators were manually filtering comments to find "which of these blocked issues need me?"

The artifact persistence feature assumes one agent per issue run. If multiple agents collaborate on the same issue in parallel, they might overwrite each other's work products. We're okay with this constraint for now — multi-agent concurrency is a later problem.

We chose OpenTelemetry over a custom metrics format because we want to ship traces to Honeycomb or Grafana eventually. But the OTel SDK is heavyweight and the metric cardinality is already creeping up. We'll need to revisit sampling and aggregation before this becomes a cost problem.

## Trade-offs

The agent thread chat is optimistic for writes but pessimistic for reads. If the backend is slow, you'll see your own messages instantly but other participants' messages might lag. We picked this because "my message disappeared" feels worse than "their message is delayed." Not sure if that's the right call long-term.

The `awaiting_human` notification feature can spam operators if agents over-use it. We added throttling (max one notification per issue per 4 hours), but that's a band-aid. The real fix is teaching agents when a handoff is worth interrupting a human.

Artifact schema validation is strict, which means agents that write non-conforming JSON will fail the save operation. This is correct behavior, but it surfaces errors late — after the agent has done the work. We need better agent-side schema hints (maybe a dry-run validate endpoint).

## Open Challenges

**Agent coordination on the same issue.** Right now, one agent per issue run. If we want multiple agents collaborating (e.g., "draft the plan" agent → "implement the plan" agent), we need artifact versioning and merge semantics. Haven't designed that yet.

**Notification fatigue.** We have the plumbing to notify humans, but no policy layer to decide when a notification is worth sending. Agents can say "this needs a human," but they can't (yet) say "this is urgent" vs. "this can wait." We'll need priority hints and human preference rules.

**Artifact discoverability.** The Deliverables tab shows artifacts attached to the current issue, but if you want to search across all artifacts (e.g., "find all agents that wrote a draft in the last week"), there's no UI for that. We need an artifact browser or a search API.

**OTel cost.** We're sending every trace span and every metric data point to our observability backend. This will get expensive fast. We need to sample traces (maybe 1% of non-error runs) and pre-aggregate metrics before export.
