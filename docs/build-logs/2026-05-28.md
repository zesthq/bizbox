# Build Log — Week of May 22–28, 2026

Seven pull requests merged. Three releases shipped. The dominant theme this week was the `awaiting-human` bridge: a three-PR arc that took the feature from a bare schema to a fully wired, production-hardened approval channel. Alongside that, Google ADK landed as a first-class agent adapter, and the ClickUp approval signal handling got a meaningful reliability upgrade.

---

## Shipped this week

### Google ADK agent adapter ([PR #72](https://github.com/zesthq/bizbox/pull/72))

Bizbox can now run agents backed by Google's Agent Development Kit. The PR adds a new adapter package covering server execution, CLI formatting, stdout parsing, and UI config/build helpers. Google ADK is registered in the shared agent type registry, adapter registries, and capability lookup — so it behaves identically to other built-in adapters from the create-agent flow through to the loadout editor. Adapter-level server tests cover event parsing and execution behaviour.

This is the first non-OpenClaw adapter to land in the core registry. The pattern it establishes — adapter package + registry registration + UI wiring in one PR — is the template for future adapters.

### `awaiting-human` bridge: configuration schema and settings ([PR #74](https://github.com/zesthq/bizbox/pull/74))

Before this week, every company using the `awaiting-human` escalation path shared the same hardcoded channel config. PR #74 adds a `company_awaiting_human_settings` table (migration 0075), a Drizzle schema, Zod validators, a full CRUD service with secret rotation via the existing `secretService`, and GET/PATCH routes at `/:companyId/awaiting-human-settings`. The React settings page, API client, and sidebar navigation are all wired. The first supported provider is ClickUp, with workspace/channel routing. The schema is designed to accept future providers without changes.

### `awaiting-human` bridge: retry and reply dedupe ([PR #76](https://github.com/zesthq/bizbox/pull/76))

The follow-up PR finalises the bridge lifecycle. Key changes: inbound event dedupe is now scoped to `(interaction_id, external_event_id)` so the same external event is safely ignored across bridge reopenings; free-text replies import as comments and wake the agent without closing the bridge; failed bridge-open retries create a fresh row instead of reopening the failed one; and heartbeat legacy delivered-interaction filtering no longer hardcodes `clickup-chat` at the dispatch boundary. Migration 0076 consolidates the final inbound event schema and dedupe index.

### ClickUp approval: non-approval reply and negative reaction handling ([PR #70](https://github.com/zesthq/bizbox/pull/70))

Non-approval replies in ClickUp `awaiting_human` workflows now explicitly resolve as rejections — the reply text is mirrored as a comment on the issue and the status transitions accordingly. Explicit negative reactions (configurable via `CLICKUP_APPROVAL_NEGATIVE_REACTIONS`, defaulting to `thumbsdown`) reject immediately without forwarding comment text. The PR also improves `ensurePathInEnv` to always prepend `NVM_BIN` to `PATH` when missing, deduplicating entries for reliable process execution.

### Awaiting-human message ID fallback in heartbeat ([PR #68](https://github.com/zesthq/bizbox/pull/68))

A targeted fix for a race condition: when the activity log is written before ClickUp notification delivery completes, the heartbeat service now falls back to the `awaitingHumanNotificationOutbox` table to resolve the correct message ID. Both `sent` and `enqueued` delivery statuses are handled. A new test covers the fallback path.

### VM resource increase: 4 GB / 4 CPUs ([PR #73](https://github.com/zesthq/bizbox/pull/73))

Both `fly.toml` and `fly.private.toml` now specify `shared-cpu-4x` with 4 GB RAM, up from `shared-cpu-2x` with 2 GB. The PR notes the cost delta explicitly: +$11.83/month per running machine at Fly's published pricing.

## Decisions

**Per-company `awaiting-human` channel config over a global default.** The settings table is company-scoped from day one. The alternative — a single global config — would have required a migration later and made multi-tenant isolation harder to reason about. The additive-only migration means existing runtime paths are unaffected until a company explicitly configures a provider.

**Bridge retry creates a fresh row, not a reopen.** When a bridge-open attempt fails, the retry path now inserts a new `awaiting_human_bridges` row rather than updating the failed one. This keeps the audit trail clean and avoids ambiguous state where a single row represents both a failure and a subsequent success.

**Dedupe on `(interaction_id, external_event_id)`, not just `external_event_id`.** Scoping dedupe to the interaction means the same external event ID can appear across bridge reopenings without being silently dropped. The trade-off is a slightly wider index, which is acceptable given the expected cardinality.

---

## Trade-offs

**VM cost increase is real and intentional.** The jump from 2 GB / 2 CPUs to 4 GB / 4 CPUs roughly doubles the per-machine compute cost on Fly. The PR documents this explicitly. The decision reflects a judgement that the current resource ceiling was causing headroom issues worth paying to fix — but it's a recurring cost, not a one-time one.

**Google ADK adapter: full test suite explicitly not requested.** The PR body states "Not run (not requested)" — the full test suite was not requested, not merely unavailable in the environment. The adapter-level server tests that were added cover event parsing and execution behaviour, but the broader integration surface is not yet verified end-to-end. Worth watching in the next cycle.

---

## Open challenges

**Bridge provider coverage is ClickUp-only.** The schema is designed for multiple providers, but only ClickUp is implemented. Teams using other channels for human approvals have no path yet. The settings layer is the right foundation; the gap is adapter implementations.

**Heartbeat message ID fallback adds a DB round-trip on every approval reconciliation.** The outbox fallback in PR #68 is correct, but it means every heartbeat cycle that encounters an `awaiting_human` interaction without a pre-populated message ID hits the outbox table. This is fine at current scale; it's worth revisiting if heartbeat frequency or agent count grows significantly.

**Google ADK integration surface is partially tested.** As noted above, the adapter landed without a full integration test run. This is a known gap, not a hidden one — but it means the first production use of the Google ADK adapter will be the real integration test.
