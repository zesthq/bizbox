# Awaiting Human Bridge For External Human Input

Bizbox will replace ClickUp-specific awaiting-human logic in `heartbeat.ts` with an `AwaitingHumanBridge` service that is scoped to issue interactions and uses provider adapters for external delivery and polling. This bridge is not a generic chat system: the external thread is transport only, while Bizbox remains authoritative through the issue interaction and the imported issue comments created from inbound human replies. We chose this shape because the current ClickUp-specific heartbeat path couples core issue workflow to one provider, while the actual product behavior we need is narrower and more stable: one company-configured external channel for awaiting-human handoffs on issue interactions.

For the first cut, the bridge applies only to issue interactions, not agent-thread asks. Identity is interaction-scoped: one active bridge exists per interaction, provider thread reuse is allowed only while that same bridge remains open, and a retry after timeout or failure creates a new bridge cycle instead of mutating the old one back into service. Channel selection is company-wide for now. The bridge lifecycle is `pending_delivery`, `waiting_for_human`, `closed`, or `failed`, with close outcomes such as `approved`, `rejected`, `expired`, `superseded`, and `cancelled`.

Company configuration for this bridge now lives behind its own Awaiting Human settings seam instead of on generic company fields. Bizbox stores one `company_awaiting_human_settings` record per company, with generic bridge fields (`enabled`, `provider`) plus provider-specific config kept in provider JSON. For ClickUp, that provider JSON stores deterministic routing (`workspaceId`, `channelId`) and the secret reference for the personal token. The UI and runtime both consume this dedicated settings module and route rather than mutating generic company settings directly.

The core service owns workflow behavior: bridge lifecycle, dedupe, polling orchestration, import of plain replies as issue comments, waking the agent after imported replies, approval and rejection resolution, timeout handling, and failure handling. Plain replies are non-terminal and keep the bridge open. Approval and rejection signals are terminal: they resolve the interaction, wake the agent, and close the bridge. Timeouts close the bridge, emit activity plus an issue-visible system note, and leave the issue workflow state unchanged. Terminal provider failures mark the bridge failed, emit activity, and add an issue-visible system note. Provider adapters such as ClickUp only own transport concerns such as send, poll, normalize inbound provider events, and best-effort close.

We are starting polling-first, not because webhook support is impossible, but because polling is sufficient for the current workflow and keeps the first extraction smaller. The adapter seam is intentionally compatible with later webhook ingestion, but webhook support is deferred rather than required in this decision. We rejected two alternatives: keeping ClickUp-specific workflow logic inside `heartbeat.ts`, because it hardcodes provider behavior into core orchestration; and building a fully generic messaging bridge now, because that would broaden the scope into chat synchronization and thread management that Bizbox does not need for the awaiting-human workflow.
